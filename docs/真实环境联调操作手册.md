本文档用于指导你在“`Docker Compose + MySQL + 真实 Cookie + API 启动任务`”场景下，完成 `creator_max_notes_count` 功能的真实环境联调。

- [故障恢复 SOP](file:///Users/monkey/Projects/demos/MediaCrawler01/docs/故障恢复SOP.md)
- [回归验证清单](file:///Users/monkey/Projects/demos/MediaCrawler01/docs/回归验证清单.md)

## 1. 联调目标

本轮真实环境联调主要验证以下内容：

- `creator` 模式能够正常启动
- `creator_max_notes_count` 能够被正确识别
- `creator_max_notes_count=0` 时保持全量抓取
- `creator_max_notes_count>0` 时，每个 creator 只抓前 N 条作品
- 作品详情、存储、评论抓取范围会跟随作品列表一起收敛

## 2. 联调前准备

开始前请确认：

- 已完成 Docker 部署基础准备
- 本地或服务器已有可用的 MySQL
- 已准备真实且未失效的 Cookie 文件
- 已选择一个你确认“作品数量明显大于 3 条”的 creator，用于观察限量效果

推荐使用下面的目录结构：

```text
MediaCrawler01/
├── .env
├── .secrets/
│   └── zhihu.cookies
├── docker-compose.yml
└── docs/
```

## 3. 环境变量建议

先复制 Docker 示例配置：

```bash
cp .env.docker.example .env
```

然后至少确认这些变量：

```env
APP_PORT=8080

MYSQL_ROOT_PASSWORD=123456
MYSQL_DB_HOST=mysql
MYSQL_DB_PORT=3306
MYSQL_DB_USER=root
MYSQL_DB_PWD=123456
MYSQL_DB_NAME=media_crawler

PLATFORM=zhihu
LOGIN_TYPE=cookie
CRAWLER_TYPE=creator
SAVE_DATA_OPTION=db

# creator 模式专用：
# 0 表示全量抓取
# >0 表示每个 creator 最多抓前 N 条
CREATOR_MAX_NOTES_COUNT=3

HEADLESS=true
SAVE_LOGIN_STATE=true
ENABLE_CDP_MODE=false
BROWSER_DATA_ROOT=/app/browser_data

COOKIE_FILE=/run/secrets/zhihu.cookies
VALIDATE_ZHIHU_COOKIE_ON_START=true
ENABLE_GET_COMMENTS=true
ENABLE_GET_SUB_COMMENTS=false
```

说明：

- `CRAWLER_TYPE=creator`：本轮联调只关注 creator 模式
- `CREATOR_MAX_NOTES_COUNT=3`：建议先用小值观察是否真的限量
- `VALIDATE_ZHIHU_COOKIE_ON_START=true`：可以提前拦截失效 Cookie，减少空跑
- `ENABLE_GET_COMMENTS=true`：方便一起验证“评论范围是否也只跟随前 N 条作品”

## 4. 准备 Cookie 文件

创建目录并放入真实 Cookie：

```bash
mkdir -p .secrets
```

把真实 Cookie 写入：

```bash
cp 你的真实Cookie文件 .secrets/zhihu.cookies
```

或者直接编辑：

```bash
vi .secrets/zhihu.cookies
```

要求：

- 文件内容只保留一行 Cookie 原文
- 不要换行拆分
- 不要把 Cookie 提交到 Git

## 5. 启动联调环境

首次或配置变更后，建议这样启动：

```bash
docker compose up -d --build
```

如果只是替换 Cookie，通常可以只重建 app：

```bash
docker compose up -d --force-recreate app
```

## 6. 启动前检查

### 6.1 看容器状态

```bash
docker compose ps
```

预期：

- `mysql` 为 `running`
- `app` 为 `running` 或健康状态正常

### 6.2 看应用日志

```bash
docker compose logs --tail=100 app
```

重点关注：

- MySQL 初始化是否成功
- FastAPI 是否正常启动
- 是否出现 Cookie 相关报错

### 6.3 看健康检查

```bash
curl http://127.0.0.1:8080/api/health
curl -i http://127.0.0.1:8080/api/health/readiness
```

预期：

- `liveness` 正常
- `readiness` 正常

如果 readiness 失败，优先检查 Cookie 和数据库。

### 6.4 检查知乎 Cookie

```bash
curl http://127.0.0.1:8080/api/auth/zhihu/status
```

预期：

- 返回 `success=true`

如果这里失败，不要继续联调 creator 任务，先按 [故障恢复 SOP](file:///Users/monkey/Projects/demos/MediaCrawler01/docs/故障恢复SOP.md) 处理。

## 7. 联调场景一：验证 `creator_max_notes_count=3`

建议先做这个场景，因为最容易看出限量是否生效。

### 7.1 启动任务

下面以知乎 creator 为例：

```bash
curl -X POST http://127.0.0.1:8080/api/crawler/start \
  -H "Content-Type: application/json" \
  -d '{
    "platform": "zhihu",
    "login_type": "cookie",
    "crawler_type": "creator",
    "creator_max_notes_count": 3,
    "save_option": "db",
    "headless": true,
    "enable_comments": true,
    "enable_sub_comments": false
  }'
```

如果你要联调其他平台，只需要把：

- `platform`
- `creator_ids`

替换成对应平台的值即可。

### 7.2 查看任务状态

```bash
curl http://127.0.0.1:8080/api/crawler/status
```

预期：

- `status` 进入 `running`

### 7.3 查看日志

```bash
curl http://127.0.0.1:8080/api/crawler/logs?limit=100
```

重点观察：

- 入口日志中出现 `creator_max_notes_count=3`
- 各平台 creator 日志开始抓取 creator 信息
- 不会无限翻页

### 7.4 结果验证

建议从下面 3 个角度看：

1. 日志角度

- 能看到 creator 启动日志
- 能看到 `creator_max_notes_count=3`
- 能看到达到限制后的停止日志

2. 数据角度

- 每个 creator 最终只写入 3 条作品
- 评论数量只对应这 3 条作品

3. 行为角度

- 任务不会继续翻到更后面的分页

如果你用的是 MySQL，可以在数据库中直接检查作品表和评论表的写入数量。

## 8. 联调场景二：验证 `creator_max_notes_count=0`

这个场景用来确认“新功能没有破坏全量抓取”。

### 8.1 启动任务

```bash
curl -X POST http://127.0.0.1:8080/api/crawler/start \
  -H "Content-Type: application/json" \
  -d '{
    "platform": "zhihu",
    "login_type": "cookie",
    "crawler_type": "creator",
    "creator_max_notes_count": 0,
    "save_option": "db",
    "headless": true,
    "enable_comments": true,
    "enable_sub_comments": false
  }'
```

### 8.2 验证点

- 日志中出现 `creator_max_notes_count=0`
- 任务会继续翻页，直到平台无更多数据
- 抓取结果明显大于 3 条

## 9. 联调场景三：验证非法值拦截

这个场景用来确认接口校验生效。

### 9.1 发送非法请求

```bash
curl -X POST http://127.0.0.1:8080/api/crawler/start \
  -H "Content-Type: application/json" \
  -d '{
```

### 9.2 预期结果

## 11. 联调通过标准

满足以下条件，可以认为本轮真实环境联调通过：

- Cookie 校验通过
- creator 任务可以正常启动
- `creator_max_notes_count=3` 时，每个 creator 只抓前 3 条作品

- `creator_max_notes_count=0` 时，仍可全量抓取
- `creator_max_notes_count=-1` 时，请求被校验拦截

## 12. 常见问题

### 12.1 日志里没有看到 `creator_max_notes_count`

排查建议：

- 确认当前任务确实是 `crawler_type=creator`
- 确认容器已经使用最新代码重建
- 确认不是旧容器仍在运行

### 12.2 传了 `creator_max_notes_count=3`，结果还是很多条

排查建议：

- 确认你看的是否是同一个 creator
- 确认旧数据没有和本次数据混在一起
- 确认当前平台已经是本轮完成的 5 个平台之一
- 重新查看任务日志，确认是否打印了 `creator_max_notes_count=3`

### 12.3 API 一启动就失败

优先检查：

- `/api/auth/zhihu/status`
- `/api/health/readiness`
- `docker compose logs --tail=100 app`
